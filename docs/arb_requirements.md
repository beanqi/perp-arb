# 合约套利程序需求文档（V1）

## 1. 目标

实现一个高性能的永续合约套利程序，只做两类核心动作：

- 按配置的价差梯度开仓
- 按配置的价差梯度平仓

参考 Astro 的开仓和平仓能力，但 V1 不做独立行情监控、告警、回测，也不做复杂策略编排。V1 重点是把高性能数据流、单线程策略处理、异步下单和订单追踪打通，同时提供一个简易前端页面用于配置和查看运行状态。

## 2. 范围

### 2.1 包含

- 多交易所永续合约双腿套利
- 梯度开仓、梯度减仓
- 交易所 API Key / Secret 配置（前端配置，后端持久化，需要加密存储）
- 简单前端页面（HTML + JS）
- 前端配置策略，后端持久化并运行
- 查看持仓、余额、活动订单
- 深度驱动的套利触发
- 本地维护快照深度和增量深度
- 下单、撤单、订单状态追踪、超时补查

### 2.2 不包含

- 独立行情监控系统
- 策略回测
- 多机分布式部署
- 与开平仓无关的 Astro 功能

## 3. 功能需求

### 3.1 策略配置与生命周期

策略的主配置入口是前端页面，不是手工编辑本地文件。

前端至少支持：

- 新增策略
- 修改策略
- 启用 / 停用策略
- 查看策略当前状态

后端至少支持：

- 接收前端提交的策略配置
- 做基础校验
- 将策略持久化到本地存储
- 将启用中的策略装载到运行态
- 程序重启后重新加载已持久化且启用中的策略

后端持久化后的策略，才是实际运行依据。前端只是配置入口和查看入口，不直接持有运行状态。

策略以“套利对”为单位配置，每个套利对至少包含：

- `id`
- `long_leg` 和 `short_leg`
- 两腿对应的 `exchange`、`symbol`
- `open_levels`
- `close_levels`
- `max_total_notional`
- `max_open_orders`
- `stale_order_query_ms`

梯度仓位语义必须固定为“增量档位”，不是覆盖档位。

例子：

```toml
[[strategy.open_levels]]
spread_pct = 1.0
notional_usd = 100

[[strategy.open_levels]]
spread_pct = 2.0
notional_usd = 100
```

语义如下：

- 价差在 `1.0% <= spread < 2.0%` 时，目标开仓量为 `100U`
- 价差在 `spread >= 2.0%` 时，目标开仓量为 `200U`

`close_levels` 语义完全相同，只是作用对象变成“当前已持有的配对仓位”。

### 3.2 价差触发

- 开仓和平仓都必须由深度触发，而不是由成交回报或轮询触发
- 默认按两腿可成交一档价格计算价差，也就是 taker 对 taker 的可执行价差
- 方向由配置决定。若配置为“买 A、卖 B”，则默认开仓价差公式为 `(bid_B - ask_A) / ask_A`，平仓时使用反向可执行价差
- 实际可下单数量必须同时受以下约束：
  - 当前档位目标仓位
  - 已有仓位
  - 两腿可成交深度
  - 交易所最小下单量、价格精度、数量步进
  - `max_total_notional`

### 3.3 API Key 与账户配置

交易所 API Key / Secret 也需要通过前端配置，并由后端持久化。

至少支持：

- 新增和修改交易所账户配置
- 基础连通性校验
- 区分不同交易所账户

敏感信息要求：

- 后端持久化时保留明确的数据边界
- 前端默认不回显完整密钥

### 3.4 查询与展示

V1 需要提供最基础的运维入口，前端为主，CLI 可作为调试辅助。

至少支持：

- 查看策略列表和启停状态
- 查看当前持仓
- 查看当前余额
- 查看当前活动订单

前端不要求复杂框架，可以是一个简单的 HTML + JS 工程，由后端提供静态资源或独立本地页面都可以。

## 4. 实现方案

### 4.1 总体线程模型

采用“IO 异步 + 策略单线程分片”的结构。

- 深度接入：`tokio` 任务
- 下单执行：`tokio` 异步模块
- 策略处理：多个独立线程
- 线程间通信：`crossbeam-channel`
- 配置与查询入口：HTTP API + 简单前端页面

核心原则：

- WebSocket 接入任务只负责收包、发订阅、保活、重连，不负责业务反序列化
- 每个策略线程独占它负责的交易对、本地深度、订单状态、持仓状态
- 热路径尽量不使用全局锁，不在多个线程之间共享可变订单簿
- 管理面和交易热路径分离，前端请求不能阻塞撮合主链路

### 4.2 深度接入与路由

每个深度 WebSocket 连接对应一个独立的 `tokio` 任务。

深度接入规则必须固定：

- 交易所支持增量深度时，优先接“快照 + 增量”或“全量快照初始化 + 增量流”
- 只有在交易所不提供可用增量深度时，才退化为订阅全量深度
- 对于增量深度的存储以及合并，采用倒序的数组来存放（因为bid和ask都是靠近盘一的地方更新频繁）不要用 `BTreeMap` 或 `HashMap` 来存储深度档位，以避免热路径的重复哈希和内存分配
- 深度的处理需要处理一些重连和丢包场景，必须在适配层实现好重建逻辑，不能把这些复杂逻辑放到策略线程里
- 每个交易所的深度能力在适配层显式声明，不能在运行时临时猜测

这个任务负责：

- 建立连接
- 发送订阅
- 维护 ping / pong 和重连
- 接收原始消息
- 按 `connection_id -> shard_id` 的固定映射，把消息投递到对应撮合线程

这个任务不负责：

- JSON 反序列化
- 本地深度维护
- 策略判断

要求在启动时就生成并记录好：

- 哪些交易对归属于哪个 `connection_id`
- 哪个 `connection_id` 归属于哪个 `shard_id`

这样路由只依赖固定映射，不在热路径做复杂查找。

### 4.3 撮合线程

每个撮合线程负责一组交易对，通常与一个深度连接的订阅分组对齐。

撮合线程必须单线程持有并处理：

- 各市场本地深度快照
- 增量深度应用状态
- 当前仓位
- 当前活动订单
- 梯度开仓 / 平仓状态
- 价差判断和下单触发
- 价差撮合由深度触发，然后基于深度查询相关策略，撮合到10档。这里可以使用simd来加速撮合。

`crossbeam-channel` 传递的事件必须是统一枚举，至少包含：

- `MarketWsRaw`
- `OrderWsRaw`
- `AccountWsRaw`
- `PositionWsRaw`
- `TimerTick`

这里的 `Raw` 指原始 WebSocket 消息负载，消息进入撮合线程后再按交易所协议反序列化。这样深度存储、增量合并、仓位和订单状态都能留在单线程里完成。

对于支持增量深度的交易所，撮合线程必须维护：

- 初始快照
- 增量序列号或更新时间校验
- 丢包或断档后的重建逻辑

对于只支持全量深度的交易所，撮合线程直接用最新全量覆盖本地状态。

### 4.4 下单执行模块

下单执行是独立的 `tokio` 异步模块，由撮合线程通过命令通道调用。

它至少要支持：

- 下单
- 撤单
- 查询单笔订单状态
- 建立订单回报连接
- 建立订单 / 持仓推送连接

职责划分必须明确：

- 撮合线程负责策略决策、订单状态机、超时判断
- 执行模块负责把命令发到交易所，并把原始回报发回对应撮合线程

为了把订单事件准确回到原线程，`client_order_id` 必须编码 `shard_id` 和 `strategy_id`。这样执行模块可以不维护复杂共享状态，只需要按 `client_order_id` 或命令上下文把消息回投给原线程。

### 4.5 订单追踪

订单状态追踪必须同时使用三类来源：

- 下单连接返回的回报
- 订单 / 持仓推送连接返回的回报
- 超时后的 HTTP 主动查询

V1 的订单状态流转至少覆盖：

- `PendingSubmit`
- `Submitted`
- `PartiallyFilled`
- `Filled`
- `Canceled`
- `Rejected`
- `UnknownNeedQuery`

规则：

- 订单长时间没有更新时，由撮合线程判定为 stale
- stale 后由撮合线程发起查询命令
- HTTP 查询结果仍然回到原撮合线程更新状态

### 4.6 性能要求

- 深度消息在 IO 任务里不做 JSON 解析
- 热路径避免全局 `Mutex<HashMap<...>>`
- 深度、本地仓位、订单状态尽量由所属线程独占
- 热路径尽量减少 `String` 分配、重复解析和重复哈希
- 通道必须是有界的，避免异常行情导致无限堆积
- 资产和持仓广播不是热路径，可以接受低频 fan-out；深度路由必须是定向投递
- 管理后台、配置保存、页面查询不能影响深度和下单热路径

### 4.7 管理接口与前端

V1 提供一个简单的前后端管理面。

后端至少提供：

- 策略增删改查接口
- 策略启用 / 停用接口
- API Key 配置接口
- 持仓 / 余额 / 活动订单查询接口
- 当前运行中策略状态查询接口

前端至少提供：

- 策略编辑页
- 账户配置页
- 持仓 / 余额 / 活动订单查看页
- 简单运行状态展示

前端实现目标是“够用、清晰、易调试”，不追求复杂交互或组件体系。

## 5. 推荐模块边界

- `config`: 配置模型、持久化模型、校验、连接分组规划
- `admin_api`: HTTP API，接收前端策略和账户配置
- `web_ui`: 简单 HTML + JS 页面
- `gateway::market_ws`: 深度连接、订阅、保活、重连、原始消息投递
- `gateway::trade_exec`: 下单、撤单、查询、订单推送、持仓推送
- `engine::shard`: 单线程事件循环
- `engine::book`: 快照深度和增量深度维护
- `engine::strategy`: 价差计算、梯度开仓、梯度平仓
- `cli`: 配置校验、查看持仓、查看余额、查看活动订单

这里先保持模块是具体结构体和函数，不要一开始就引入过多 trait 或插件化抽象。

## 6. 分步任务

### 任务 1：项目骨架与配置模型

目标：

- 搭好目录结构
- 定义策略、账户、持久化数据模型
- 定义事件枚举、命令枚举、`shard_id / connection_id / strategy_id`
- 提供基础 HTTP API 和简单前端页面骨架
- 打通“前端提交策略 -> 后端校验 -> 持久化 -> 装载运行”
- 启动时完成连接分组和线程分片规划
- 提供基础查询入口，CLI 可保留为调试辅助

完成标准：

- 能从前端提交策略和账户配置，后端完成持久化，并打印出明确的连接分组和分片规划结果

### 任务 2：深度接入与撮合线程骨架

目标：

- 实现多 WebSocket 深度连接
- 完成订阅、保活、重连
- 对支持增量深度的交易所，实现“快照 + 增量”维护
- 对不支持增量深度的交易所，实现全量深度维护
- 原始深度消息通过 `crossbeam-channel` 定向发送到对应撮合线程
- 撮合线程实现单线程事件循环
- 在撮合线程里完成快照深度和增量深度维护

完成标准：

- 指定交易对的深度消息能够稳定进入正确线程，并在该线程内按交易所能力维护本地 order book

### 任务 3：策略核心

目标：

- 实现价差计算
- 实现梯度开仓和梯度平仓
- 实现目标仓位计算
- 按仓位、深度、精度、限额生成下单命令
- 避免重复开仓、超限开仓和错误减仓

完成标准：

- 给定深度变化和已有仓位，线程内能稳定算出“当前应该新增多少仓位”或“当前应该减多少仓位”

### 任务 4：下单执行与订单追踪

目标：

- 实现异步下单、撤单、查单
- 接入订单回报和订单 / 持仓推送
- 把原始订单事件准确回投到原撮合线程
- 实现 stale 订单补查
- 在线程内完成订单状态机更新，并能查询当前订单 / 持仓状态

完成标准：

- 一笔订单从下单到成交、撤单或超时补查，都能在原线程看到完整状态流转

## 7. 实现约束

- 先按单机单进程实现
- 先保证线程归属和状态归属清晰，再做性能微调
- 先支持最少必要的交易所，不要一开始做大而全适配层
- 先把“深度触发 -> 下单 -> 状态追踪 -> 平仓”主链路跑通，再补外围能力
- 前端先求简单可用，不要一开始引入复杂前端工程体系
